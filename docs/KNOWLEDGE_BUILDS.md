# 商品向量构建隔离与原子发布

更新日期：2026-10-23。

## 原问题

旧实现的profile_id只由模型配置计算。同一profile增量更新时，每批提交直接覆盖product_knowledge中的活动记录；后续Embedding失败不会撤回已提交批次。“全部就绪才切换profile”只隔离新模型配置，没有隔离活动profile内的数据更新。

## 当前实现

profile_id表示模型配置；每次构建另生成唯一build_id。knowledge_builds记录构建状态、源快照哈希和数量，knowledge_build_products保存该构建的完整文档与向量，knowledge_settings同时保存active_profile_id与active_build_id。

```text
活动B1保持不变
  → 新建building状态的B2
  → 向B2复制相同配置、相同文本/哈希的已有向量
  → 只为剩余商品计算Embedding，按批写入B2
  → 短事务锁住描述源表，核对源快照、完整记录、维度及构建元信息
  → 在同一事务把B2设为ready，并将活动指针切到B2
```

查询只读取一次捕获的active_build_id，且构建必须ready、profile匹配当前模型。即使随后有新发布，原构建仍保留，因此该次查询不会跨构建拼接向量。工具返回的价格等业务字段仍从商品视图读取。

每批可以独立提交到候选B2，但不会写入活动B1。Embedding失败、维度错误、返回数量错误、源描述改变或发布事务失败，都不会把半成品发布为活动索引。失败构建的成功批次保留，下次新建B3时按完整文本、哈希、模型配置和维度复用，减少重复Embedding。

构建进程使用会话级advisory lock覆盖整个构建，第二个构建立即拒绝；Embedding期间不持有长数据库事务，正常检索无需获取该锁。发布时源表SHARE锁短暂阻止变更，避免“校验后、切换前”源描述又改变。

## 失败时究竟会怎样

例如A、B的描述变化，B2已复制未变的C并算好A，计算B失败：活动指针和B1全部向量保持原样，B2标为failed，不被检索；下次只需补算B。新事务发布前没有覆盖旧活动记录。

这不是源业务数据的历史快照。若商品描述已经更新，旧活动向量与当前商品描述不一致，现有fresh_rows检查仍会过滤旧候选，召回数量可能下降；源描述过滤仍发生在候选截断后。本改动解决半成品进入活动索引，不声称解决了所有召回完整性问题。

如果数据库在提交时失联，客户端可能不知道提交是否成功，应重新连接核对活动指针；不能断言“报错就一定没发布”。异常清理只将building改为failed，不把已提交的ready构建降级。数据库完全不可用时可能留下building记录，它仍不是活动可读构建。

## 已有索引迁移

在新版代码目录执行：

```bash
python build_product_knowledge.py --migrate-only
python build_product_knowledge.py
```

先停止旧建库脚本。第一条在事务中创建新结构，将原活动profile的向量原样复制成legacy构建并设置active_build_id；幂等执行，不重新Embedding、不删除旧表。第二条正常创建独立构建，未变向量直接复用。迁移成功后重启旧CLI，以使用新版检索代码。

旧product_knowledge仅为迁移保留，不再用于新版查询或增量写入。新部署在首次正常建库时也会自动初始化结构。--dry-run只读统计，不执行迁移。不要只部署新版检索代码却跳过已有库迁移，否则向量检索无法就绪，业务搜索可能回退词法路径。
