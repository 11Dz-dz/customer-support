# 日期、金额、退款与并列数量的受控输出

项目：`/root/rivermind-data/Agent/example/langgraph_olist_example/`。

## 遇到的问题与改进方向

### 日期名称被误解释

旧回答将due_at说成付款截止日。根因是让模型自行解释源字段。核对源数据字典后固定为订单约定交付日期，付款与签收保持未知，不修改原日期来迎合回答。

### 工具金额正确，但自由生成的组合清单与合计不一致

M05.2曾写约130.63，而所列两件实际为85.23，加入第三件为166.22。增加后端多方案Decimal计算和展示前复核，模型只能选择已核实的商品，不能编写单价或合计。

### 退款实际复用，回答却说重复登记并承诺通知

P08暴露了工具操作与文字解释相反的问题，也出现未接入的审核通知、附件和修改能力承诺。增加显式操作、资金状态和能力字段，程序区分新建、复用、历史记录及失败，不把申请状态当作退款到账。

### 最低价并列与末项同价混淆

M06.2将4.99的3条同价套用到最低价2.29。分别统计完整过滤范围中的极值价位和末项价位，渲染时对应各自数量。

### 原始事实被模型过度改写，错误草稿还可能先流出

旧复核发现当前可售、材质、用途和否定特性等无依据表述。最终回答改成受校验的展示计划和来源逐字引用，关键事实由程序渲染后分段发送，失败时保守回退；不能因此承诺原始描述本身正确。

### 改造后发现的路由和摘要遗漏

M01查明细时遗漏状态，补为有证据的订单摘要固定项；M04选购小计被分给账单，补充购买前报价归销售、已有订单金额归账单的职责边界。修改后重新回归，保留失败版本的原始报告。

下面记录具体实现、验证和代价。想先用具体例子理解，请看 [通俗版总总结](IMPROVEMENTS_READABLE_20261021.md) 第5、6节。

## 业务事实由谁生成

Supervisor输出TaskPlan，程序合并、校验并调度任务。明确只读任务由task_execution映射工具并生成展示计划；开放任务由专家在受控ReAct中取证并选择AnswerPlan。

collect节点用本任务允许引用的证据构造TaskResult，调用render_business_result生成销售与账单内容。商品编号必须有工具证据；模型提供的解释只允许引用对应商品的原始描述。金额、日期和状态由程序填写；无效计划使用保守证据展示。answer节点汇总本轮turn_outputs，处理工单与待补充信息，再发布一份最终正文。

技术节点也先经过collect：健康结果从工具快照渲染；错误码从search_error_code结果展示。所有专家草稿都不是各自直接发给用户的最终答案。

源描述自身的翻译错误不会因引用约束自动消失；这套机制约束关键事实，不证明模型理解和全部自然语言都正确。

## 日期

数据库保留`due_at`，返回中新增`date_labels`和`date_semantics`：

- `purchase_at`：下单日期。
- `due_at`：订单约定交付日期，对应源SalesOrderHeader.DueDate。
- `shipped_at`：发货日期。
- 付款截止日期：未知；签收记录：未提供。

字段释义依据微软源建表脚本的扩展说明：

https://github.com/microsoft/sql-server-samples/blob/master/samples/databases/adventure-works/oltp-install-script/instawdb.sql#L6313

展示层使用固定字段映射，不接受模型另写日期名称，也不把约定交付日期当作实际签收。

## 金额和多方案报价

已有订单使用订单成交单价、明细金额和订单应付总额，不用目录价重算历史订单。

calculate_price支持单商品与组合模式。组合参数示例：

```json
{
  "bundles": [
    {"items": [{"product_id": 915, "quantity": 1}, {"product_id": 946, "quantity": 1}]},
    {"items": [{"product_id": 915, "quantity": 1}, {"product_id": 946, "quantity": 1}, {"product_id": 941, "quantity": 1}]}
  ],
  "budget": "100"
}
```

一次查询同一数据库快照中的真实目录价，使用Decimal计算各方案；上述两组分别为85.2300和166.2200，预算100时第一组在预算内、第二组超预算。

每组是独立备选，不将所有方案的合计再累加成一笔订单。重复商品先合并数量；模型不能传单价或合计；非法数量、超限方案、未知商品、非有限预算或0标价都拒绝报价。任一商品无有效价格时整次报价失败，不悄悄漏项给出低价。

展示前再次核对单价×数量、明细合计和预算关系。未核实的币种不输出货币单位，税费、运费和优惠不加入目录估算。

## 退款

request_refund通过统一ToolResult返回，下列业务字段位于data中：

- `operation`：`created_application`或`existing_application`。
- `already_exists`：明确是否复用。
- `data.status`：申请状态；不等于外层工具执行status，也不等于资金状态。
- `funds_action`：`not_executed_by_this_system`表示本次没有执行资金退款。
- `capabilities`：目前支持登记/复用，修改原因、上传凭证和审核通知为false。

程序分别生成新建、复用、历史记录复用或失败的说明。即便申请状态是approved，也会说明它不代表资金已退回。模型省略退款栏目时，实际成功执行的退款操作仍会在正文中报告。

当前没有审核执行和通知服务；程序不会承诺审核通知或退款到账。历史信息会标明来自会话此前记录，避免将旧状态当作新查询结果。

## 并列数量

查询继续在全部符合价格、关键词、颜色及尺寸条件的目录范围内执行。保留`boundary_price_tie_count`，新增：

- `extreme_kind`：本次价格排序的min或max。
- `extreme_price`、`extreme_tie_count`：首项所在极值价位及该价位在完整过滤范围内的数量。
- `boundary_price`：本次列表末项价位。

例如最低5项中，最低价2.29对应1条，列表末项4.99对应3条。程序分别解释“最低价没有并列”和“4.99有3条同价”，不会把边界并列套用到最低价。空结果的极值和并列字段为null。

## 流式与持久化

模型原始草稿不直接作为业务正文发送。专家节点先将消息交给collect；collect保存配对的AI工具调用和ToolMessage、更新任务，并生成各项展示内容；answer统一汇总后发出verified_answer_chunk，chat_runtime转发给CLI。

最终公开回答作为AI消息保存，流式片段拼接结果与持久化公开正文一致。首段最终正文需要等待相应取证和校验，不是模型原始Token一产生就显示。路由和工具进度可先由日志事件显示。

图入口身份校验与公共入口会话锁仍生效。工具证据只来自授权任务；当前访问失败不能用旧成功结果掩盖。模型异常时通过TaskEvidenceRecorder恢复已完成证据，并在回答中说明未完成部分。

## 文件

路由提示补充了购买前报价与已有订单金额的职责边界，避免上轮回答中关于税费、运费或支付的说明把选购追问带到账单节点。

- `adventureworks_service.py`：日期释义、双重并列统计、退款操作标记、组合报价。
- `answer_contract.py`：JSON展示计划、证据选择、关键事实渲染、引用校验与分段。
- `langgraph_supervisor_1.py`：工具组合模式、业务模型草稿标签、展示计划提示及节点集成。
- `chat_runtime.py`：已校验正文的自定义流转发。
- `tests/test_answer_contract.py`：错误草稿隔离、真实数据库、组合金额、退款与流式持久化检查。
- `tests/test_session_identity.py`：保持底层错误码和身份隔离断言，改为核对用户可读的拒绝正文。

原始评测报告及AI复核记录保留。
