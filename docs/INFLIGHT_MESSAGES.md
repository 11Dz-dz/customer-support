# 处理中追加消息、排队与停止（2026-10-31）

## 原来的问题

用户先说“推荐一款自行车”，系统处理时又想说“预算500以内”。旧版输入框禁用，后端同会话返回409；新条件无法进入处理，用户只能等待并重新发送。直接并发调用同一个thread_id又可能让两份流程互相覆盖任务和历史。

## 现在怎样工作

一个会话仍只有一个后台执行者。新消息先持久化到PostgreSQL的web_run_inputs，后端确认接收后才在页面显示回执。消息有独立去重编号，处理期间追加不会启动第二份同会话Agent。

页面处理期间保持输入框可用，并提供两种发送方式：

- **补充当前任务**（默认）：在图的检查点读取，追加真实HumanMessage，再由原规划器更新任务。预算变化保留原用途、对象、数量及其他未清除条件；重新核实受影响任务，未发布的旧答案被替换。
- **作为下一条问题排队**：当前答复交付后再执行。同一后台运行可包含多个顺序执行的对话段，每段有独立的模型链路和回答消息。

例如“推荐一款自行车”后补“预算500以内”：如果还没确认交付答案，新条件会触发规划更新；如果旧检索已完成，就在原任务上增加预算并重新检索，之后只发布更新后的答复。目录里没有符合预算的整车时，保持真实空结果，不把配件当整车补足。

## 在哪些时机读取

1. Supervisor开始规划前，读取已到达的补充输入。
2. 规划后、安排下一项专家任务前，再次检查。
3. 专家执行并收集其完整工具证据后，检查是否需要更新规划。
4. 最终回答节点开始时及确认交付时检查。可能创建人工工单时，先确认输入边界，再写工单。

这一版不会在正在执行的模型请求或SQL中途强行插入消息。专家节点可能包含多次模型/工具交互，补充消息会等该节点完成，再在图边界处理。已经完成的工具记录保留，不能伪装成未执行。

更新规划时按任务ID保留未受影响的任务和答案，按revision删除已过期的答案。新条件无法可靠规划时给出澄清，保留任务记录，不发布旧条件下的答案。补充输入沿用同一个请求期限及共享模型/工具预算，不无限重置额度。

## 如何处理“答案正要发出时，又来一条消息”

消息接收和最终交付判断共用数据库事务锁。新消息只有两种明确结果：

- 在交付确认前入库：作为补充读取，重新规划后再交付。
- 在交付确认后入库：标为followup，持久化等待下一段。它不会被悄悄丢弃，也不承诺已经影响上一份答复。

显式排队的消息是FIFO边界。其后的消息也转为排队，不越过独立问题偷偷影响其他任务。页面回执会显示实际处理方式。每段公开回答有自己的message_id，前端按ID接收片段，避免追加的用户气泡抢走正在生成的回答。

## 停止与重启

页面“停止后续处理”采用协作式停止：等当前模型/工具执行结束，在检查点结束后续流程，保留已完成证据和停止说明；未处理消息标为cancelled。停止不会撤销已完成操作，也不会自动重放。答案已确认交付时，停止接口返回ANSWER_COMMITTED，避免错误宣称已阻止交付。

浏览器断线只断开订阅，后台继续处理；重新打开会话可以看到持久化输入及原运行。每条输入的接收/纳入状态和SSE游标都可恢复。服务被关闭或进程崩溃后，遗留活动运行及未确认输入标记interrupted，消息正文仍保留；用户核实后再明确提出处理请求，不自动重放业务操作。

输入入库和LangGraph检查点是不同事务，不能宣称任意崩溃下所有外部操作都恰好执行一次。已有权限、业务去重和人工工单约束继续生效。

## 状态、容量与日志

| 输入phase | 含义 |
|---|---|
| pending | 已接收，尚未交给当前处理段 |
| included | 已纳入当前处理段，尚未交付本段答复 |
| answered | 本段已结束并交付答复；不等于业务一定成功 |
| cancelled | 停止时尚未处理的消息已取消 |
| interrupted | 流程中断，处理结果需要核实 |

同一活动运行最多接收8条输入（含最初一条），每条最多4000字符；超限返回429，不静默丢弃。默认仍是一个Uvicorn worker、2个不同会话并发。普通规划最多执行4项，处理中追加后累计最多12次专家调度，并继续受12次工具请求、4次商品搜索、8轮专家模型调用和原请求期限限制。路由规划调用另计。

结构化日志新增inflight_input_consumed，记录输入数量、ID和是否最终检查点，不记录原文或模型推理。Web SSE增加input回执，仅提供当前授权会话的用户文本、消息ID、mode和phase；普通页面不显示请求编号。历史按实际接收/答复时间排序，比较统一时间戳，避免时区字符串顺序错误。
