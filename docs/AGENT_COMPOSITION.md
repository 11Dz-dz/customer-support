# 提示词、专家配置与销售 Skill

## 为什么改

此前路由规则、三个专家的提示词、工具定义、状态和图连接集中在 `backend/agent/langgraph_supervisor_1.py`。想查“销售顾问能调用什么工具”或修改一条说明，需要在大文件中寻找，也容易混淆操作说明和真正的权限检查。

本轮借鉴 Harness-Agent 的文件组织方式，先把这些职责分开，再按维护需要拆出商品推荐与商品对比操作说明。原有结构化任务、条件校验、候选精选、权限、预算和事实渲染继续负责执行。没有引入 DeepAgents、MCP 服务或新的依赖。

## 商品对比具体怎么工作

例如用户问“比较适合通勤的自行车，预算500以内”：

1. 原 Supervisor 仍先生成并校验结构化任务，决定它是否属于销售的 `product_search`。
2. 原流程按任务条件检索，统一候选池继续作为事实依据。
3. 专家构造模型消息时，先加载推荐 Skill 中的共同候选选择步骤；如果任务查询或本轮最近一条真实用户输入包含“对比、比较、区别、差异、compare、comparison”等表达，并且销售配置允许，才附加商品对比说明。
4. 说明要求先复用本轮证据、核对对象类别和用途、区分缺少描述与没有功能，资料不足可以少选；仅资料不足且原预算允许时补充只读查询。
5. 模型仍提交原来的 JSON 回答计划，程序继续核验商品 ID、描述引用和价格后展示。

Skill 本身不查询数据库，也不会因为加载就增加一次模型调用或强制调用工具。它只是让同一销售专家在推荐任务中读取候选选择说明、对比任务再读取一份补充说明。模型仍可能理解或选择错误，不能据此保证回答质量提高。

两个 Skill 都只覆盖进入模型执行的销售商品检索。指定商品 ID 的 `product_detail` 保留原来的确定性读取路径，不为加载 Skill 额外调用模型；未匹配到上述表达的对比任务也不保证加载；这不是独立的多轮意图分类器。一个输入含多个任务时，原文中的对比表达也可能使销售检索多加载一份说明，说明只作用于当前销售任务，不新增对比目标。普通推荐只加载推荐 Skill；目录统计、订单和技术任务不加载销售 Skill。没有新增 `product_compare` 任务类型。

## 为什么不会因为 Skill 放宽权限

配置列出“允许给这个专家哪些工具”，操作说明告诉模型“这些工具该怎样使用”，程序校验负责“这次调用是否真的允许”。三者职责不同。

配置读取器只接受现有三个专家及各自工具白名单，禁止把订单工具交给销售，禁止把已停用的聊天退款写工具重新加入。Skill 也只能来自代码批准的本地文件，不能由用户消息指定或下载，不提供脚本执行能力。管理员修改开发文件属于代码变更，需要重新验证。

例如模型读完对比说明后，把 `max_price=500` 改成999调用检索，原 `guarded_tool_call` 仍检查与当前任务是否一致；不一致就返回 `TASK_TOOL_NOT_ALLOWED`，不执行真实查询。客户身份和订单归属也仍由原程序检查。

## 排查与维护

模型每次构造提示词且加载 Skill 时，现有事件链记录 `skill_loaded`，字段包括 Skill 名称、版本、文档 SHA256、任务 ID 和 revision；同一任务多次推理可能出现多条加载事件。事件不增加提示词正文、用户问题或工具结果正文。仍可通过现有 request/thread/trace 关联查找。

第一阶段曾按原始字符串提取提示词；本次仅销售提示词有意移出推荐步骤，历史 sales 哈希保留但不再声称当前销售提示词逐字一致。其他提示词仍进行原哈希比对。除回答计划外，读取器将源文件换行拼接起来；源文件一行一条规则便于阅读，换行暂不作为模型格式。回答计划的原有换行保留。纠正说明只替换原来的 `{field}` 和 `{reason}`，不执行用户模板。

这些文件在进程内缓存，修改后需要重启服务；不是网页实时编辑或用户可定制 Prompt。后续改变规则时应更新对应版本、测试和行为记录，不能把本轮的“原字符串一致”证明套用到未来修改上。

## 自己测试

在原网页发“比较两款适合通勤的自行车，预算5000以内，说明选择的商品描述依据”，再在原事件日志或 LangSmith 中查看 `skill_loaded`。普通“推荐一款自行车”不应仅为加载说明而多调用模型。指定ID的商品详情继续走原来的确定性读取。

重跑这组真实测试的命令是 `python -m evals.composition_runner --live`，会产生新的报告并消耗模型额度；不会重写旧记录。只读取已有本轮记录可使用 `python -m evals.composition_runner --review 路径/report.json`，不调用模型或工具，且拒绝覆盖已有复核文件。


## 商品推荐拆分与重复规则整理（当前维护结构）

问题：推荐步骤仍集中在 sales.md，商品对比又重复描述候选选择，改一套规则需要检查多处。

改进：将候选选择、推荐数量、不同型号、描述引用、少选与不推荐等步骤统一放到 product-recommendation 1.0.0。product-comparison 更新为1.1.0，只保留比较对象、维度及缺失信息等补充步骤。普通 product_search 加载推荐一份；对比检索按固定顺序加载推荐、对比两份。配置禁止只启用对比而缺少共同步骤。用户文本只能影响是否加载批准的对比说明，不能选择文件、增加工具或改变权限。

销售基础提示词继续保存工具分工、事实来源、价格范围、币种/库存未知、历史标价与成交价区别等通用边界。原有 JSON 协议、程序条件校验和事实渲染不变；新增 Skill 不建立新任务类型、不增加图节点或模型调用轮次，也没有修改检索排序算法。指定商品ID、目录排序、订单、报价等确定性路径继续直接执行。

今后维护：修改推荐与候选选择的方法查推荐 Skill；修改比较方法查对比 Skill；修改通用事实边界查 sales.md；修改检索、价格计算或强制校验查原业务代码。推荐/对比不新增自由输出字段。文件缓存仍需重启服务才刷新。

真实百炼 DS 专项9个场景、10轮问答、13次模型调用全部成功，功能规则通过：六个原场景、E03两轮预算、一次完整推荐和一次完整对比。实际模型输入确认普通推荐加载推荐一次、对比零次；对比问答加载推荐和对比各一次。两种回答均选择755、760，独立SQL核对类别、预算、数量和商品存在性。未做用途相关性或答案质量评审、完整80场景回归及压力验收，不宣称解决此前暂缓的检索相关性问题。


服务范围基础说明独立在 prompts/scope.md，每次由路由和专家读取，不由 Skill 触发。无关请求的固定回复、任务保护和最新验证见[服务范围](SERVICE_SCOPE.md)。


商品推荐后的相对价格比较属于计划条件处理，不另建 Skill。当前路由提示词加入相对价格说明，原 router 哈希同 sales 一样保留作历史，不再声称当前两个资产与初版逐字一致；其他资产仍按原基线检查。详见[多轮相对价格](RELATIVE_PRICE.md)。


## 同款颜色、尺寸与价格条件

“别的颜色”现在按已展示商品的数据库型号直接查询，并保留另一规格；普通查询展示实际款式并说明价格差额和是否符合原条件，明确预算不变时严格筛选。原推荐任务保留，后续报价引用实际展示的款式。原因、代码分工和实际验证见[同款规格说明](PRODUCT_VARIANTS.md)。


## 商品条件统一与目录问答

包含、排除、颜色备选、价格比较和多轮修改使用统一条件协议；目录覆盖问答直接查分类数据。问题、原因、代码位置、首轮真实测试发现及验证边界见[统一商品查询说明](CATALOG_QUERY_CONTRACT.md)。
