# 商品查询统一条件与目录问答

更新：2026-11-03。本文解释当前代码如何处理一类商品问题，而不是为某句话添加固定回复。

## 问题与原因

用户问“除了自行车还有什么交通工具”，DS生成了排除自行车的查询，但旧的程序词语匹配看见“自行车”后，把查询类别设成了自行车。随后系统在自行车里检索交通工具，再通过推荐精选给出通用失败回复。

这暴露出三个结构问题：程序和模型在重复解释类别；旧标量字段难以表达排除及备选；目录覆盖问答进入了用途推荐流程。

## 当前职责

模型一次规划业务意图及条件关系，程序验证条件结构、来源、数值、更新范围及工具参数。程序不再用“出现某个类别名”等同于“必须包含该类别”。

| 用户要什么 | 当前执行 |
|---|---|
| 店里卖什么、除了某类还有什么类别 | catalog_query / overview，查询真实分类与记录数 |
| 按颜色、价格等列出、计数、排序 | catalog_query / list、count、stats，参数化SQL |
| 根据用途推荐 | product_search，统一条件先过滤，再混合召回与描述精选 |
| 已展示商品的其他颜色、尺寸 | product_variants，按真实型号关联；保留原规格查询规则 |

没有额外增加一个负责逐轮复核的LLM，也没有更换专家架构、Embedding或引入新的数据库。

## 包含、排除和组合如何表达

`catalog_query.py` 定义受限条件语言：大类category、具体商品类型product_type、颜色、尺寸、目录标价五个字段。前四者支持eq/ne/in/not_in，标价支持eq/ne/lt/lte/gt/gte。product_type由`product_taxonomy.py`维护实际子类编号和中英文名称，如头盔helmet，不能只落成整个骑行装备大类。类型SQL和候选核对使用同一适配数据。

每组conditions之间是“并且”，groups之间是“或者”。同一字段的多个备选值用in；普通筛选只有一组。例如“红色或银色，并且600以内”：

```json
{"groups":[{"conditions":[
  {"field":"color","operator":"in","values":["Red","Silver"]},
  {"field":"price","operator":"lte","values":[600]}
]}]}
```

只有完整备选方案才分多组，例如“红色500以内，或者银色800以内”。共同的自行车类别要放入每一组。最多4组、总共24项条件；不是任意SQL或无限嵌套逻辑。

字段名、比较符来自白名单，值作为SQL参数；同一套条件还用于Python候选核对。缺失属性保持未知：例如“不为黑色”不会把颜色缺失的商品自动视为已证实的非黑色。

## 多轮更新和防止覆盖

`query_update`是模型写入口，包含用户原文片段、当前输入索引和操作；`parameters.catalog_filter`是程序保存的查询状态，从规划器可写schema中隐藏。

- 新查询replace；同一任务amend，只改本轮涉及的字段。跨字段备选修改按确定的分配规则组合，超过复杂度限制时拒绝执行。
- 清除条件用clear和明确字段列表；已支持的“颜色不限”等明确清除表达也从实际引用原文核实，不能把模型只省略字段误当作已经清除。继续旧任务通常不允许replace整份覆盖；用户明确改查整个目录时可重置范围，引用应包含动作和范围，未通过时共享原有的一次纠错额度。普通改颜色不能借此清掉旧预算。
- “自行车600以内”后补“不要黑色”，保留类别和预算；再说“预算1000”，只修改价格。
- 新任务通过task_id隔离，不自动沿用另一项任务的预算。多个任务不能共用一段未明确归属的条件依据。
- 新价格值必须出现在引用的本轮原文中；复述已确认的同一条件是无操作，不要求伪造新来源。明确提出新预算却复述旧值仍拒绝。相对价格继续由程序读取已展示商品的数据库标价推导，并与原备选方案逐组取交集，不放宽原预算。
- 工具调用必须携带与任务一致的条件，删除排除项、放宽预算或更换规格会被拦截，原始调用记录保留。

旧检查点和旧适配器仍可使用标量字段及field_updates；后端将它们编译到同一条件体系。使用新query_update时，旧类别/颜色/价格词语规则不会再次覆盖它。旧字段作为简单条件的兼容镜像，组合条件以catalog_filter为准。

原文片段真实、JSON合法，不等于语义必然正确。模型仍可能误解否定、条件归属或OR范围；程序没有声称证明全部自然语言含义。针对明确“只看/仅限”等正向范围，额外检查它没有被排除项代替；仅有排除条件不能冒充完整的正向目标。这个有界完整性检查不决定类别值，缺漏会在执行前交给原有一次规划纠正额度处理。

## 目录信息与空结果

目录能力由当前AdventureWorks适配器声明：自行车整车、零部件、骑行服装、骑行装备。交通工具在已知分类中只映射自行车整车；不把头盔、车架、服装当成交通工具。

overview从数据库读取分类记录数，单独报告未分类记录。排除自行车后，可说“当前已分类目录没有记录其他交通工具类别”；还存在未分类数据时，不能扩展为“全目录绝对没有其他交通工具”。分类覆盖也不能证明实时库存。

结果区分目录范围、完整条件范围内无匹配、召回无候选、候选用途无法确认、条件冲突以及服务失败。推荐召回为空时，现有全目录范围核对也使用同一套条件；不能把服务失败或描述不足当作目录不存在。目录问答和精确筛选不经过推荐精选。

## 修改位置

`catalog_query.py`负责条件类型、合并、SQL编译、候选匹配和目录说明；`task_state.py`定义可写补丁与持久化字段；`constraint_updates.py`衔接旧路径和多任务来源；`adventureworks_service.py`统一目录/检索过滤并增加overview；`product_knowledge.py`、`retrieval_pipeline.py`核对两路召回和候选；`task_execution.py`、`tool_execution.py`负责直接执行及参数保护；`answer_contract.py`负责事实展示；路由获得目录能力及组合规则。

## 开源参考与统一查询初版验证

本次静态阅读NVIDIA Retail Shopping Assistant固定版本`50468a94dc9adfa9bdd72d884647418a5e341afd`的目录工具、能力边界和过滤测试，以及Sierra tau-bench目录类型工具、LangChain StructuredQuery。借鉴职责和条件表达；没有复制整套系统，也没有运行这些外部项目。本项目使用自己的受限条件模型及PostgreSQL编译器。

首轮20个真实模型开发场景保留原报告：发现了只读状态被当作写入口、普通AND被错误分成OR组等问题，随后调整规划schema和组合规则。Q14原参考把宽泛“自行车配件”仅算作装备，忽略零部件；依据实际分类修正独立SQL参考，同时保留原始失败记录。后续同题又发现模型只保留“非整车”、漏掉配件正向范围，导致服装也计入。这是真实规划缺漏，不能当作评分器误判；新增执行前正向范围完整性检查和目录父类能力说明。

后续多轮测试又发现：模型复述旧预算被误当成新编辑，以及“颜色不限”只从模型输出省略字段而没有删除旧约束。程序现按字段差异忽略已确认的不变项，并识别有原文依据的明确清除。保留各版失败轨迹；逐轮独立SQL复核不只检查最后一轮。预留验收题一旦用于发现问题，后续即按回归题处理，不再宣称未见盲测。

最终测试数量、批次、部署及限制以本轮服务器记录为准：`evals/catalog_query_20261103/`、`logs/query_deployment_20261103.json`、`logs/query_verification_20261103.json`。专项脚本为`python -m evals.catalog_query_runner --live`；预留验收题使用`--phase acceptance`，它们仍是人工编写的模拟题，不是独立真实用户验收。
