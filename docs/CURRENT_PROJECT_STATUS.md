## 1. 项目能不能收尾

以“基于样例数据、可运行和演示的多Agent客服系统”为目标，可以进入收尾阶段，不必继续堆功能。目前没有发现必须阻止该目标收尾的新故障；这不等于已经证明没有任何缺陷。

以真实客户使用的生产客服应用为目标，尚未完成：没有真实登录和商家业务接口、完整政策资料、真人在线工作台及独立验收。本项目不宣称具备这些能力。真实业务接入与政策知识库此前已暂缓，不把这些暂缓项反复当作必须立刻开发的任务。

下一步更适合自己演示、检查回答并整理简历。发现可复现的新问题后再修改，不需要为了“还能优化”持续重构。

| 多轮与隔离 | PostgreSQL检查点、thread_id、服务器客户映射、同会话互斥、订单归属校验。 | thread_id不是用户身份；管理员映射不是登录系统。 |
| 结构化任务记忆与摘要 | task_state定义任务，调度器继承/清除条件；程序生成精简任务摘要，结合最近对话生成查询。 | 不是另一个模型总结全部历史；用途偏好主要保存在文本，检索query仍有200字符限制。详见完整说明17.3–17.6。 |
| 回答事实 | 模型给回答计划，程序用工具证据展示金额、日期、状态和商品；关键金额由业务代码计算。 | 受控表述较保守；未核实信息保持未知，不能保证语义理解百分之百正确。 |
| 部分完成与重试 | 保留成功项；用户要求时，仅按原参数有限重试合格的失败只读操作；总尝试最多3次。 | 权限拒绝、无效参数、未知错误和业务写入不走普通失败重试。 |
| 工具协议 | 11个业务工具统一版本、执行状态、错误码、说明、data及retryable；兼容旧记录。 | 最低字段检查不等于所有业务语义都已得到形式化证明。 |

## 3. 数据和模型分别负责什么

- DeepSeek负责理解问题、任务规划和专家判断，通过API调用，不需要在这台服务器部署大语言模型。
- 本地multilingual-e5-small ONNX模型只负责生成检索向量，使用CPU；当前实现不要求GPU。
- PostgreSQL保存样例商品、订单和明细、描述关联、商品向量、会话身份映射、退款申请及人工工单。
- `agent_checkpoints` schema保存会话检查点；`customer_service` schema保存客服业务数据及相关记录。可通过配置将检查点放到单独数据库。
- 价格、订单金额、日期和状态查询使用业务SQL，向量检索不决定这些事实。

订单和目录来自微软AdventureWorks虚构样例，没有连接实际店铺。支付、发票、库存、优惠、实时物流、币种及售后政策等缺少可靠依据时，不补造结论。

## 4. 现有服务器怎么启动和使用

当前服务器环境、数据库、数据和向量已经配置。日常运行无需重新安装、导入数据或重建向量。

```bash
cd /root/rivermind-data/Agent/example/langgraph_olist_example
/opt/conda/envs/agent/bin/python run_multiturn.py --thread-id demo-guest-20261022 --verbose
```

上例是游客会话，可查商品，不能查订单。会话ID应由可信服务管理；同一已验证用户重启后使用原ID继续，不让用户任意指定他人的会话ID。

需要演示订单时，管理员先为**没有历史的新会话**绑定样例客户，再启动该会话。例如29825是已有示例中使用的客户编号：

```bash
/opt/conda/envs/agent/bin/python manage_session_users.py bind --thread-id demo-bound-20261022 --customer-id 29825
/opt/conda/envs/agent/bin/python run_multiturn.py --thread-id demo-bound-20261022 --verbose
```

如示例会话ID已被使用，应选择新的ID。不能把已有游客历史补绑成客户，也不能将已有客户会话换绑给他人。绑定是管理员演示配置，不是生产登录流程。

| 聊天输入 | 作用 |
|---|---|
| `quit` / `exit` / `退出` | 退出命令行交互。 |
| `/history` | 查看身份校验后的公开历史。 |
| `/new` | 为同一用户新建会话。 |
| `/human` | 不依赖模型创建或复用人工工单。 |
| `/handoffs` | 不依赖模型查看当前会话最近5条工单。 |

`--no-stream`使用一次性展示；默认流式输出仍经过事实展示规则。修改代码后需重启旧CLI进程。

## 5. 人工到底是谁来处理

目前由能登录服务器的管理员模拟人工。系统不会自动找来客服人员，也没有发送消息给任何人。

```bash
/opt/conda/envs/agent/bin/python manage_handoffs.py list
/opt/conda/envs/agent/bin/python manage_handoffs.py show H-替换为完整工单号
/opt/conda/envs/agent/bin/python manage_handoffs.py claim H-替换为完整工单号 --operator admin
/opt/conda/envs/agent/bin/python manage_handoffs.py resolve H-替换为完整工单号 --operator admin --note "实际核对经过和处理结论"
```

状态为待人工处理、人工处理中、已标记处理完成；处理人标记用于审计，不等于账号认证。管理员按thread_id/task_id定位原始证据，不能仅凭模型转述认定业务结果。标记工单完成不代表退款到账，也不替代实际核对。

## 6. 当前图怎么执行

identity_guard → supervisor → scheduler → 专家 → collect → scheduler，直到没有可执行任务，再由answer统一回答。身份检查先于历史使用；collect收集和渲染单项结果，answer统一汇总并处理人工工单。

明确只读任务走程序映射，开放任务走受控ReAct。task_state与task_scheduler管理多轮参数继承和任务依赖；工具协议、预算、SQL权限、事实展示和期限由程序执行。并不是每个专家节点都要再调用一次专家模型。
