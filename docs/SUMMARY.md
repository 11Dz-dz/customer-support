## 一、项目是什么？

### 1. 项目定位

`customer-support` 是一个基于 Python、LangGraph、DeepSeek、PostgreSQL 和 pgvector 的多 Agent 客服系统。

它使用 AdventureWorks 样例业务数据，模拟商品咨询、订单查询、账单问题、技术支持、退款申请登记以及人工工单处理等场景。

项目的重点不只是让大模型回答问题，而是让大模型在一个具有明确业务约束的系统中工作：

- 能够理解用户提出的多个业务目标。
- 将复合请求拆成结构化任务。
- 根据任务类型、参数和依赖决定执行顺序。
- 调用 SQL、商品检索及其他业务工具。
- 验证工具结果和客户访问权限。
- 保留已经成功取得的证据。
- 在预算、超时或部分失败时控制执行。
- 根据经过验证的业务事实生成最终回答。
- 在特定异常下创建人工处理工单。
- 通过自动化测试和 Agent 场景评测检查系统行为。

### 2. 技术架构

| 技术 | 在项目中的作用 |
|---|---|
| Python | 业务逻辑、任务状态管理、工具执行和测试 |
| LangGraph | 管理有状态的图执行、节点跳转和多轮检查点 |
| DeepSeek API | 用户意图理解、任务规划和专家 Agent 推理 |
| PostgreSQL | 商品、订单、会话身份、工单及向量相关数据 |
| pgvector | 存储和查询商品描述向量 |
| multilingual-e5-small ONNX | 本地生成商品与查询向量，使用 CPU |
| Pydantic | 验证任务计划、工具结果及其他结构化数据 |

DeepSeek 负责语言理解和规划；本地 Embedding 模型负责向量化；PostgreSQL 负责业务事实查询和持久化。

**不能把这些职责混在一起：大模型生成的判断不自动成为可信业务事实，向量相似度也不能替代 SQL 中的价格、订单状态或客户归属。**

### 3. 项目当前的能力边界

这是一个可以运行和演示的样例客服系统，不是已经完成生产接入的商业客服平台。

现已有本地账号登录、Web聊天和工单管理页；仍没有真实店铺订单接口、外部身份系统集成、真实支付退款、实时库存、完整售后政策知识库或实时人工坐席。

退款由用户在订单页确认提交，管理员审核；聊天只指引和只读查询进度，不执行资金退款。

## 二、先理解整个项目的主流程

整个系统最重要的源码入口是 `langgraph_supervisor_1.py`。

完整主链路可以概括为：

```text
用户输入
   |
   v
run_multiturn.py
   |
   v
chat_runtime.py
统一请求配置、会话锁、超时和流式输出
   |
   v
identity_guard_node
校验会话归属及已有历史状态
   |
   v
supervisor_node
调用模型生成结构化任务计划
   |
   v
prepare_plan / 任务状态准备
验证任务、参数、依赖和历史状态
   |
   v
scheduler
选择当前可执行任务
   |
   v
sales / billing / tech_support
   |
   +-- 确定的只读任务
   |      |
   |      v
   |   task_execution.py
   |      |
   |      v
   |   直接映射业务工具
   |
   +-- 开放式任务
          |
          v
       专家 Agent
          |
          v
       guarded_model / guarded_tool_call
          |
          v
       业务工具
   |
   v
collect_node
收集工具证据、更新任务状态、生成事实展示内容
   |
   +------ 还有可执行任务 ------> scheduler
   |
   v
answer_node
汇总本轮已完成的结果、未完成事项及人工工单信息
   |
   v
END
```

图中的核心思想是：**模型负责理解与规划，程序负责调度与执行，数据库提供业务事实，结果验证层负责约束最终展示。**

一次图执行结束不代表整个会话结束。用户继续输入时，系统会根据同一个有效 `thread_id` 恢复之前的状态，再处理下一轮请求。

## 三、任务规划与调度：项目最核心的控制逻辑

### 1. 为什么需要多个任务？

用户可能在一句话里提出多个业务要求。

例如：

> 推荐一款适合长途骑行的自行车，再查询我的订单，并介绍订单里的第一件商品。

这至少包含三个目标：

1. 推荐自行车。
2. 查询订单。
3. 查询订单中某件商品的详情。

如果把整句话直接交给一个 Agent，让它自由调用工具，容易出现职责混杂、参数丢失、重复查询和任务遗漏。

因此，项目先规划任务，再由程序调度执行。

### 2. `TaskPlan` 与 `ConversationTask`

这两个概念不能混为一谈。

**`TaskPlan`：规划结果。**

模型生成的结构化任务计划，描述本轮要做什么、需要哪些参数、任务之间有什么依赖。

它仍然是需要校验的模型输出。即使 JSON 格式正确，也不意味着任务一定合理。

**`ConversationTask`：程序管理的业务任务。**

程序验证计划后，将任务纳入结构化状态管理。执行时会读取相应的任务字段，恢复成需要的任务对象，并使用程序认可的参数和状态。

任务包含的关键信息包括：

- `task_id`：任务标识。
- `kind`：任务类型。
- `agent`：负责的专家。
- `parameters`：任务参数。
- `status`：任务状态。
- `depends_on`：前置任务的任务 ID 列表；`dependency_mode` 描述如何使用前置任务结果。
- `operations`：具体工具操作记录。
- `retry_failed` 等重试控制信息。

图检查点需要保存可序列化状态，因此任务在状态中可能以字典等形式存储；这不意味着每次调度都重新向模型询问任务计划。

### 3. 任务计划在什么时候转换？

正确的理解是：

1. Supervisor 调用模型生成任务计划。
2. 程序解析并验证计划的字段、参数、任务编号及依赖。
3. 程序将合法任务纳入图状态中的结构化任务记录。
4. Scheduler 根据当前状态选择任务。
5. 执行节点读取当前任务，在需要时构造或恢复 `ConversationTask` 对象。
6. 工具执行结果被收集，任务状态被更新。
7. 调度器继续处理其他可执行任务。

**不应该每执行一个工具就重新生成整份任务计划。** 任务规划与任务执行是两个不同阶段。

### 4. Scheduler 的职责

Scheduler 不负责再次理解整句用户输入，也不负责执行所有工具。

它主要判断：

- 哪些任务已经完成或取消。
- 哪些任务仍然等待补充参数。
- 哪些任务的依赖已经满足。
- 哪些任务可以执行。
- 下一项应该交给哪个专家节点。
- 当前任务执行后是否需要继续调度。

当前项目按顺序执行任务，并没有启用专家任务之间的并行执行。

### 5. 任务依赖与参数继承

例如：

```text
任务 T1：查询订单
任务 T2：介绍订单里的第一件商品

T2.depends_on = [T1.task_id]
```

T2 需要依赖 T1 实际查询到的订单明细。

如果 T1 返回的第一件商品 ID 是 `776`，程序才可以把这个有证据的 ID 传给 T2。

不能因为模型猜测某个商品 ID 很可能正确，就把它当成订单实际包含的商品。

还要区分两个场景：

- “推荐自行车，再查询订单”：两个独立任务，不必强行建立依赖。
- “查询订单，再介绍订单中的商品”：第二项依赖第一项的真实结果。

### 6. 多轮补充与取消

如果任务缺少订单号，程序可以将其保留为等待补充的状态，而不是阻塞 Python 进程。

下一轮用户补充订单号后，程序只继续对应的待处理任务，不必重复已经完成的商品推荐。

如果存在多个等待订单号的任务，用户只提供一个编号但没有说明对应哪项任务时，程序应该要求澄清，不能随意把编号分配给某个任务。

取消某项任务也不代表其他独立任务都应该取消；取消任务更不代表撤销已经提交的业务操作。

## 四、专家 Agent 与确定性工具执行

### 1. 三个专家的职责

| 专家 | 主要业务范围 |
|---|---|
| `sales` | 商品查询、推荐、详情和购买前报价 |
| `billing` | 订单、支付及账单相关查询 |
| `tech_support` | 技术问题和错误代码解释 |

Supervisor 负责规划，专家负责各自领域的任务，Scheduler 决定执行顺序。

### 2. 为什么已知任务不需要每次都调用模型？

假设任务已经明确为：

```python
task.kind = "order_query"
task.parameters.order_id = 43659
```

程序已经知道需要查询订单以及订单号是什么，就可以直接映射为：

```text
query_order(order_id=43659)
```

这条路径由 `task_execution.py` 中的 `read_operations()` 和 `execute_operations()` 实现。

直接执行的优点：

- 减少不必要的模型调用。
- 降低延迟与 API 消耗。
- 减少模型修改参数或选择错误工具的机会。
- 更容易测试和验证。

开放式商品推荐等任务则仍然需要专家 Agent 根据实际检索证据作出判断。

### 3. `seed_product_search()`

商品推荐往往需要先取得候选商品，才能让专家根据真实数据选择和解释。

因此，`seed_product_search()` 会先执行初始商品检索，为专家提供候选证据。

它不是最终回答生成器，而是提前取得业务证据的执行步骤。

## 五、结果处理与证据验证：为什么工具成功还不够？

这一部分涉及：

- `tool_result.py`
- `task_result.py`
- `answer_contract.py`
- `collect_node`
- `answer_node`

### 1. `ToolResult`：统一工具结果协议

正式业务工具使用统一结果结构，包含：

```json
{
  "schema_version": 1,
  "status": "empty",
  "error_code": "PRODUCT_NOT_FOUND",
  "message": "没有找到该商品。",
  "data": {},
  "retryable": false
}
```

这里的字段必须严格区分：

| 字段 | 含义 |
|---|---|
| `schema_version` | 结果格式的版本号 |
| `status` | 本次工具执行的结果状态 |
| `error_code` | 供程序处理的固定错误码 |
| `message` | 经过控制的业务说明 |
| `data` | 结构化业务数据 |
| `retryable` | 是否具备重试资格 |

**`schema_version=1` 不代表执行成功。**

即使工具失败，只要返回的是符合第 1 版协议的规范化结果，版本号仍然可以是 1。

常见状态包括：

- `success`：工具正常执行，取得可用结果。
- `empty`：查询正常执行，但没有匹配数据。
- `invalid_argument`：参数不合法。
- `forbidden`：操作不被允许。
- `temporary_error`：明确的临时故障。
- `error`：其他未分类错误。

`empty` 不等于 `failed`。查询成功但没有数据，与数据库连接失败，是不同情况。

`retryable=true` 也不代表程序会立即自动重试。重试仍然受到工具类型、错误码、角色权限、原始参数和尝试次数等限制。

### 2. `TaskResult`：任务级结果

`ToolResult` 表示单次工具执行的结果。

`TaskResult` 保存任务状态、当前及历史工具证据、待补字段、操作记录和重试信息等，不包含回答正文字段。`collect_node` 根据它和回答计划生成展示文本，再将文本放入 `turn_outputs`，由 `answer_node` 汇总。

例如，同一订单任务中，订单查询和支付查询成功，发票查询已经尝试但返回临时错误，整理后的任务状态为 `partial`。

需要注意：`collect_task_result()` 主要根据已观察到的工具结果和操作账本判断状态，没有通用地核对“所有本应执行的工具是否都已执行”。如果只有前两项成功证据，完全没有发票调用记录，单靠该函数仍可能得到 `completed`。正常确定性订单路径会按任务参数及 `focus` 安排查询；这与通用的漏执行检测是两回事。

因此：

**工具成功不等于任务成功，任务成功也不等于整轮请求的所有任务都已完成。**

### 3. `AnswerPlan` 与最终回答

`answer_contract.py` 定义了 `AnswerPlan` 及其解析、验证和业务结果渲染逻辑。

`AnswerPlan` 是回答计划，不是最终展示给用户的自然语言回答。

它描述程序应该展示什么，例如：

- 回答处理类型 `kind`，例如 `data`、`ask_order`；它不同于业务任务类型 `order_query`、`product_search`。
- 需要展示的业务字段。
- 商品 ID 或订单 ID。
- 需要引用的解释或证据。

回答计划可以由两条路径产生：

1. 开放式专家 Agent 根据实际工具结果生成计划 JSON。
2. `task_execution.py` 根据确定的任务参数直接生成计划 JSON。

随后由 `parse_answer_plan()` 解析和验证，`render_business_result()` 根据经过验证的工具证据生成业务文本。

确定性执行路径不需要额外调用模型来决定已经明确的任务字段。

### 4. 为什么不能直接相信模型的回答计划？

即使计划格式合法，也可能出现：

- 商品 ID 不在工具证据中。
- 订单 ID 不属于当前客户。
- 展示了没有经过核实的支付状态。
- 将约定交付日期误说成实际签收日期。
- 编造库存、币种或退款政策。
- 把计算错误的金额直接展示给用户。

因此，程序需要检查计划引用的证据，并由业务代码填充关键事实。

金额使用合适的十进制计算；订单状态、日期和商品信息从实际业务记录读取；缺乏可靠来源的信息保持未知。

最终 `answer_node` 汇总本轮所有任务的结果，只输出一份完整的用户回答，而不是将每个专家的中间草稿都作为独立答案发送出去。

## 六、`collect_node`：整个任务执行与结果整理之间的桥梁

`collect_node` 是理解项目最重要的节点之一。

它不是简单地将专家输出追加到对话历史中，而是将工具执行证据转化为程序可以管理和展示的任务结果。

其职责包括：

1. 收集当前专家执行产生的工具消息。
2. 关联工具调用及其结果。
3. 规范化工具返回值。
4. 更新 `OperationRecord`。
5. 判断任务是否成功、部分完成或失败。
6. 根据证据验证 `AnswerPlan`。
7. 生成当前任务的事实展示内容。
8. 更新任务状态，交回 Scheduler 继续执行。

例如：

```text
query_order          succeeded
check_payment_status succeeded
query_invoice        failed / temporary_error（已调用但查询失败）
```

第三项存在明确的失败记录，所以不能只根据前两项成功就标记整项任务成功；这种情况应为 `partial`。如果第三项根本没有调用记录，当前通用收集函数并不能自动发现它被遗漏，不能把这个例子理解成已经实现所有工具的漏执行检查。

同样，如果一个任务失败，但另一个任务已经成功，程序应保留成功任务的结果，不应让失败项覆盖全部结果。

这是整个项目实现部分完成、任务恢复和可靠汇总的关键。

## 七、操作账本、工具缓存与重试

涉及模块：

- `task_operations.py`
- `tool_execution.py`
- `task_evidence.py`

### 1. `OperationRecord`

每次逻辑上的工具操作都有自己的记录，包含操作 ID、工具名、参数、状态、尝试次数、错误码、重试资格和人工复核标记等信息。

`operation_id()` 根据规范化后的工具名称与参数生成稳定标识。

它与 `tool_call_id` 不同：

- `tool_call_id`：关联一次具体工具调用及其返回结果的 ID；模型发起的调用和程序主动执行的调用都可以有该 ID。
- `operation_id`：标识逻辑上相同的工具操作。
- `task_id`：标识业务任务。
- `thread_id`：标识会话。

同一个只读操作被模型调用两次，可能产生两个 `tool_call_id`，但对应同一个逻辑 `operation_id`。

### 2. 工具调用预算

根据当前项目说明，默认限制为：

| 范围 | 工具请求处理额度（超额拦截） | 实际商品搜索额度 | 专家模型轮数 |
|---|---:|---:|---:|
| 单个任务 | 6 次 | 最多 2 次 | 最多 4 轮 |
| 整个用户请求 | 12 次 | 最多 4 次 | 最多 8 轮 |

这里的 6／12 是守卫允许继续处理的请求额度，不保证模型提交的调用总数或请求计数器永远不超过上限。程序先计数，再拦截超额调用；缓存命中和被拦截的请求也会计数。例如提交 8 次不同的只读调用，在单任务 6 次额度下，计数可以是 8，真正执行工具 6 次，其余被拦截。缓存、无效参数等还可能使实际执行更少。

规划调用另行计算。

这些限制是为了避免模型在已经有足够证据时继续重复查询。

到最后的专家模型轮次时，程序会限制工具调用能力，让模型根据已有证据回答或说明信息不足。

### 3. 只读工具缓存

相同的只读工具及规范化参数，可以在同一次执行中复用成功结果。

例如：

```text
query_order(order_id=43659)
query_order(order_id=43659)
```

第二次相同请求可以复用第一次查询结果。

缓存不仅减少重复执行，还会关联当前工具调用的 ID 与结果消息，维持 LangChain 工具消息协议的正确性。

它不是跨用户、跨会话的永久缓存，也不是会话记忆。

退款申请等写操作不能直接使用普通只读缓存规则。

### 4. `retry_operations()`

只有满足相应条件的失败操作才会进入重试集合，包括：

- 操作状态为 `failed`。
- 操作明确允许重试。
- 工具属于只读工具。
- 当前 Agent 有权调用该工具。
- 错误码属于允许重试的临时错误。
- 未超过尝试次数限制。
- 如果指定了需要重试的操作 ID，还必须匹配指定集合。

项目的正常恢复流程要求用户明确请求重试失败部分；不是所有临时错误都会自动无限重试。

例如：

```text
query_order          succeeded
check_payment_status failed / temporary_error
```

重试时只重新执行 `check_payment_status`，保留已经成功的订单查询证据。

### 5. `TaskEvidenceRecorder`

如果工具已经执行成功，随后模型调用超时，不能把整项任务简单视为没有结果。

`TaskEvidenceRecorder` 通过回调记录工具开始、结束及异常信息，在后续模型执行失败时恢复已经观察到的工具调用和结果。

这样，系统可以区分：

- 工具没有执行。
- 工具执行失败。
- 工具成功，但后续模型没有完成最终回答。

已完成的证据会继续被收集和使用，不必无差别重跑所有工具。

## 八、请求期限与上下文预算

涉及模块：

- `request_deadline.py`
- `context_budget.py`
- `chat_runtime.py`
- `postgres_config.py`
- `embedding_client.py`

### 1. 请求截止时间

项目默认业务执行期限为 90 秒，通过 `REQUEST_TIMEOUT_SECONDS` 配置。

模型单次完整响应默认最多等待 60 秒，同时不能超过本次请求的剩余时间。

项目还将剩余期限传递给 SQL 查询、本地向量推理等执行步骤。

需要区分：

- `ModelCallTimeout`：一次模型调用超时。
- `RequestDeadlineExceeded`：整个请求的截止时间耗尽。

超时后保留已完成工具证据，并按条件处理失败操作。

客户端取消等待不保证远端模型计算已经停止；数据库检查点、工单创建和资源释放也可能产生额外收尾时间。因此，90 秒是业务执行预算，不是保证整个 Python 进程在第 90.000 秒被强制终止。

### 2. 上下文预算

`context_budget.py` 负责控制模型输入的消息副本。

当前设计主要按序列化消息的字符数控制输入规模，而不是精确 Token 数。

主要步骤：

1. 优先保留最新用户问题和必要的公开对话。
2. 关联工具调用及对应工具结果。
3. 压缩过长的工具结果。
4. 在预算内选择可以保留的工具组。
5. 重建有序的模型输入。

它不会因为缩减模型输入，就删除 PostgreSQL 检查点中的完整历史。

这与任务隔离也不同：

- `scoped_history()`：限制当前任务可以引用哪些历史证据。
- `expert_context()`：控制这些内容中哪些可以在输入预算内交给模型。

重要业务事实应从结构化任务结果中提取，而不是完全依赖模型回忆被压缩或省略的历史。

## 九、商品查询与混合检索

涉及模块：

- `adventureworks_service.py`
- `catalog_filters.py`
- `product_knowledge.py`
- `embedding_client.py`
- `build_product_knowledge.py`
- `schema_product_knowledge.sql`

### 1. 为什么不同的商品问题需要不同的查询方式？

项目区分精确查询、目录分析和开放式商品推荐。

| 用户需求 | 合适的执行方式 |
|---|---|
| 查询明确商品 ID 或型号 | 直接查询数据库 |
| 找最贵的商品 | SQL 全目录排序 |
| 统计符合价格条件的商品数量 | SQL 过滤与计数 |
| 统计价格分布 | SQL 聚合 |
| 推荐适合长途骑行的商品 | 关键词与语义混合召回 |
| 查询订单里的某件商品 | 先查询有权限的订单，再使用真实商品 ID 查询详情 |

向量召回只能提供候选商品，不能证明全目录极值、完整数量或真实业务状态。

### 2. 混合检索

`product_knowledge.py` 负责商品文档和向量检索相关逻辑，`adventureworks_service.py` 负责数据库查询及业务筛选。

混合检索主要包含：

1. 将用户查询转成检索文本。
2. 执行关键词检索。
3. 使用本地 Embedding 模型生成查询向量。
4. 执行语义向量检索。
5. 对两路候选进行 RRF 名次融合。
6. 根据真实商品表数据返回商品信息。

RRF 按候选在各自结果列表中的排名进行融合，而不是直接把关键词分数与向量距离相加。

### 3. 价格与类别过滤

用户的预算要求应该成为查询的硬条件。

例如“500 以内，适合长途骑行”，程序会提取 `max_price=500`，并将其应用到关键词检索和向量检索的 SQL 条件中。

不能先取最相关的少量商品，再把超预算商品删除，因为这可能遗漏其他符合预算且相关的商品。

当前能力边界：

- 价格条件支持两路检索过滤。
- 商品类别支持相应的目录与检索条件。
- 颜色、尺寸在精确目录查询中支持，但尚未作为语义推荐两路召回的统一硬条件。
- 目录默认排除 0 标价。
- 向量候选不是全目录完整排名，不能用它证明全局最贵。
- 价格从商品表读取，不写入描述向量，因此单纯价格变化不要求重新生成 Embedding。

### 4. 商品向量如何构建？

每件有描述的商品形成一份短文档，包含名称、型号、颜色、尺寸、重量和中英文描述。

本地 `multilingual-e5-small` ONNX 模型生成 384 维向量。商品描述和查询使用相应的 `passage`、`query` 前缀。

项目不是任意长文档的通用分块系统，也不会自动为没有描述的商品补写介绍。

### 5. 向量索引一致性：当前状态

这是之前讨论过的重要问题，必须以仓库最新状态为准。

旧实现的问题是：同一 `profile_id` 下的增量构建可能直接覆盖活动商品向量；如果后续 Embedding 失败，已经提交的批次不会自动撤销，活动索引可能出现新旧数据混杂。

**当前仓库文档已记录该问题的修复设计：**

- `profile_id` 标识 Embedding 配置。
- `build_id` 标识一次独立索引构建。
- 新版本在独立的数据范围内构建。
- 未变化的文档可以复用旧向量。
- 变化或新增的文档重新生成向量。
- 完整性验证通过后，才在事务中原子切换活动索引指针。
- 构建失败时，旧活动索引不会被半成品覆盖。

相关说明：[KNOWLEDGE_BUILDS.md](https://github.com/11Dz-dz/customer-support/blob/main/docs/KNOWLEDGE_BUILDS.md)。

根据该文档，新增的 `tests/test_knowledge_builds.py` 包含 10 项真实 PostgreSQL 故障和一致性测试，项目自动测试总数达到 210 项并通过，未调用 DeepSeek。

这是一项仓库文档中的验证记录，不代表本次对话重新执行了测试。

当前仍有边界：旧构建没有自动清理；源描述变化后，旧活动向量与当前商品描述可能暂时不一致，查询会过滤过期候选，召回数量可能下降。构建隔离解决的是半成品发布问题，不代表所有召回完整性问题都已解决。

## 十、数据导入、数据库 Schema 与持久化

### 1. 数据导入

`import_adventureworks.py` 负责读取、校验和导入 AdventureWorks 原始数据。

主要流程：

1. 检查五份源文件。
2. 读取并转换字段。
3. 校验列数、主键、外键关联和业务金额。
4. 检查源文件哈希。
5. 使用 PostgreSQL 事务和批量导入机制写入数据。
6. 记录导入哈希和行数。

原始文件虽然使用 `.csv` 扩展名，但按无表头 TSV 格式读取。

重复导入不是无条件清空并重建数据。如果源文件与导入记录一致，且数据库状态符合预期，可以返回 `already_imported`；如果数据库已有数据却缺少可靠导入记录，或者数据行数不一致，程序应拒绝静默继续。

### 2. `schema_postgres.sql`

该文件定义业务数据库结构，包括商品、订单、订单明细及相关描述等表，以及主键、外键、唯一约束、检查约束、索引和视图。

Python 侧的数据校验与数据库约束不是互相替代的：

- Python 校验提前发现数据问题并提供具体错误。
- 数据库约束保护最终存储状态，防止其他写入路径绕过业务校验。

`product_catalog` 等视图可以把商品基本信息与关联描述组合起来，简化业务查询。

### 3. 会话检查点

`conversation_persistence.py` 使用 PostgreSQL 保存 LangGraph 检查点。

相同 `thread_id` 可以在后续请求或进程重启后恢复会话状态。

同一会话使用数据库 advisory lock 进行互斥，避免两个请求同时修改同一份对话状态。

`END` 表示本轮图执行结束，不代表永久关闭会话。

## 十一、身份校验与数据隔离

涉及模块：

- `session_identity.py`
- `manage_session_users.py`
- `identity_guard_node`

### 1. `thread_id` 不等于 `customer_id`

`thread_id` 标识一段对话；`customer_id` 标识业务数据中的客户。

服务器通过可信的会话映射记录：

```text
thread_id → customer_id
```

例如：

```text
demo-bound-001 → 29825
demo-bound-002 → 29672
```

用户在聊天中声称自己属于另一个客户，不能修改服务器保存的绑定关系。

### 2. 身份验证在什么时候执行？

`identity_guard_node` 位于 Supervisor 之前。

程序先验证会话映射和已有检查点状态，再允许进入后续任务规划与业务执行。

订单查询还必须检查订单的客户归属。工具执行成功、返回格式合法，并不代表当前会话有权访问该订单。

### 3. `ContextVar`

`customer_identity_scope()` 在执行上下文中设置可信的会话和客户身份。

订单工具通过 `current_customer_id()` 获取当前身份，并校验工具调用的会话标识与数据库绑定是否一致。

上下文退出时会恢复原值，防止身份信息泄漏到其他执行范围。

### 4. 当前身份机制的限制

命令行继续使用管理员预配的演示会话映射；Web已增加本地账号认证，管理员创建账号时关联样例客户，后端按账号创建并绑定会话。它不包含外部SSO或真实商家身份接入。

`thread_id` 不是登录凭证。游客可以咨询商品，但不能查询客户订单。

已有历史的游客会话不能直接补绑为客户会话，已经绑定客户的会话也不能随意更换归属。

## 十二、人工工单与退款申请

涉及模块：

- `human_handoff.py`
- `manage_handoffs.py`
- `task_operations.py`
- `schema_postgres.sql`

### 1. 哪些情况会转人工？

主要包括：

- 用户明确要求人工处理。
- 业务写操作结果不确定，需要人工核对。
- 同一只读操作持续失败。

空结果、缺少参数或一次普通查询错误，不应一律创建人工工单。

### 2. 工单如何存储？

`human_handoffs` 保存工单主体；`human_handoff_events` 保存创建、领取和完成等事件。

系统支持活动工单去重、领取、完成和审计。

工单快照只保存必要的任务类型、状态、错误码、工具名称和尝试次数等信息，不应该复制完整聊天、订单正文、密钥或异常堆栈。

### 3. 退款申请不等于真实退款

用户在订单页确认提交待审核申请；管理员审核不调用支付平台转账。

如果同一订单已经有活动退款申请，程序会复用现有申请，避免重复创建。

如果写操作提交结果不确定，程序应保留人工复核标记，而不是盲目再次提交。

人工工单被标记为完成，也不代表退款已经到账。

### 4. 人工处理的边界

管理员可以使用CLI或Web工单页领取和完成；仍没有实时坐席聊天、自动通知和在线人工回复。

人工工单是可持久化的待处理队列，而不是已经完成的真人客服服务。

## 十三、日志、健康检查与运行入口

### 1. `chat_events.py`

统一生成结构化运行事件，包括请求、任务、工具开始和结束、执行耗时、缓存命中与拦截原因等。

事件写入 `logs/events.jsonl`，也可以通过 LangGraph 的自定义事件流传递给调用方。

`request_id` 标识一次请求，`thread_id` 标识一个会话。

普通日志不应该记录完整用户问题、完整工具参数、订单正文或密钥。

### 2. `chat_runtime.py`

统一管理请求运行配置、会话锁、截止时间、回调和流式输出。

主要入口：

- `invoke_turn()`：执行并返回完整结果。
- `stream_turn()`：流式执行，接收回答和运行事件。

外部调用方应优先使用这两个入口，而不是把底层 `app.invoke()` 当成完整的应用请求入口。

### 3. `health_monitor.py`

按需检查 PostgreSQL、容器资源和 DeepSeek 模型列表接口。

健康检查不是持续监控告警平台；模型列表接口成功，也不代表账户一定有余额或真实生成请求一定成功。

### 4. 命令行入口

- `run_multiturn.py`：交互式聊天。
- `manage_session_users.py`：管理员配置会话客户映射。
- `manage_handoffs.py`：管理员查看、领取和完成工单。
- `run_evaluation.py`：运行 Agent 评测。
- `import_adventureworks.py`：导入业务数据。
- `build_product_knowledge.py`：构建商品向量索引。

管理员 CLI 和部分数据库配置属于本次学习中按要求跳过的内容，后续不需要重复详细讲解，除非出现新的具体问题。

## 十四、测试与 Agent 评测

### 1. `tests/`

自动化测试主要验证：

- 函数和模块行为。
- 工具结果协议。
- 身份与权限。
- 任务调度和状态。
- 超时、异常与证据恢复。
- 工单创建、去重和状态变化。
- 数据库事务与索引构建一致性。

历史记录：截至 2026-10-23，索引隔离测试加入后，自动测试总数为 210 项并通过。

2026-10-24 的记录：新增 12 项 DeepSeek 协议与评测检查测试后，全套为 222 项；在隔离目录和正式项目目录分别运行通过。新增测试覆盖程序资料视图、旧记录、任务隔离、推理字段保留、流式／非流式 HTTP 请求格式和降级回答漏判。

这些自动测试使用真实 PostgreSQL、假模型、假 Embedding 或模拟 HTTP 服务，不调用真实 DeepSeek。真实模型调用在下面的场景评测和协议检查中单独记录。

### 2. `evals/`

评测场景覆盖商品目录、订单、检索、多轮会话、权限与业务边界等。

基础集合有 60 个场景、71 轮对话，其中开发集 45 个场景，留出集 15 个场景，12 个开发场景被标记为冒烟集。

2026-10-22 的历史版本连同其他专项集合，记录了 112 个模拟场景、157 轮对话；今天没有将这 112 个场景全部重跑。

2026-10-24 另运行新增路由集合的 v2 回归：24 个场景、47 轮对话，24／24 通过，包含 49 次真实模型调用。还单独验证了两次原生工具闭环，共 4 次真实模型请求，明确开启 thinking。两组检查的范围和报告分开记录，详见第十九节。

评测会记录：

- 最终回答。
- 路由和工具调用。
- 工具参数与执行结果。
- 数据库副作用。
- 关键业务事实是否正确。
- 模型调用、延迟及可用的 Token 统计。
- 自动评分和严重失败。

### 3. 如何理解评测结果？

单元测试通过，不代表完整 Agent 一定回答正确。

自动评测通过，也不代表已经达到生产级可靠性。

还需要区分：

- 开发集：用于反复改进。
- 留出集：用于检验改动的泛化表现，但该项目的留出集已经参与多轮回归，不能再称为完全未见的盲测。
- 真实模型评测：会消耗 API 额度。
- 独立人工验收：不能用自动规则通过率代替。

评测比较前，还需要检查数据集哈希、参考标签、评分器版本、模型配置和数据快照是否一致。

## 十六、整个项目最重要的十条理解

1. **模型生成的是计划，不是执行事实。** 任务计划必须经过程序校验才能进入执行流程。
2. **任务与操作是不同层级。** 一个任务可以包含多个工具操作；一个操作成功不代表整个任务成功。
3. **调度由程序负责。** 模型负责理解意图，Scheduler 负责选择可执行任务。
4. **确定性任务不必重复调用模型。** 已知参数的只读操作可以直接映射到业务工具。
5. **工具结果需要统一协议。** `schema_version` 表示格式版本，`status` 才表示执行结果。
6. **成功不代表有数据，也不代表有权限。** `empty` 是正常查询结果；客户归属必须单独验证。
7. **重试应针对失败的操作。** 已成功的证据要保留，不能无差别重跑整个任务。
8. **回答计划不等于最终回答。** `AnswerPlan` 需要与工具证据核对，再由程序渲染关键业务事实。
9. **持久化不等于授权。** `thread_id` 只能定位会话，不能证明用户身份。
10. **测试通过不等于生产级可靠。** 自动化测试、场景评测和独立人工验收有不同的证明范围。

## 十九、2026-10-24 补充：DeepSeek 消息兼容与评测补强

本节补充今天已经部署的改动；之前的学习内容和历史验证记录继续保留。详细说明见 [DEEPSEEK_PROTOCOL.md](DEEPSEEK_PROTOCOL.md)。

### 1. 为什么搜索到了商品，推荐仍然没有完整完成？

之前在“推荐一款自行车，再查询我的订单”一类场景中，程序初始搜索已经成功，接着销售模型请求返回 HTTP 400。程序保留商品资料并给出降级回答，所以屏幕上有商品，但任务实际为 `partial`。

原因有两层：程序执行的检索被包装成模型发起的工具调用历史；当前安装的 SDK 又在后续请求序列化时漏掉了模型原始的 `reasoning_content`。这属于输入消息及接口适配问题，不能解释为检索没有执行。

### 2. 程序自己检索，结果怎样交给模型？

```text
程序调用 search_products，已经取得真实商品结果
    ↓
调用记录和工具结果仍由原有消息结构保存、用于账本及事实核对
    ↓
发送给模型时另建资料视图：
“程序已执行搜索，条件是……，实际结果是……，请据此推荐。”
    ↓
DeepSeek 根据候选资料选择商品并给出回答计划
```

不是把一条工具调用消息交给模型，让工具重新执行。调用与结果早已存在，改变的是发送给模型看的表示。接口中的资料消息使用 `user` 角色，但内容明确标为程序资料或历史答复，不作为新的用户需求，也不提升为系统指令。

### 3. 模型真正调用工具时怎样处理？

```text
DeepSeek 返回真实工具调用及原始 reasoning_content
    ↓
图中的 ToolNode 执行相应工具
    ↓
程序把工具结果连同模型原始调用信息传回
    ↓
DeepSeek 继续推理并完成回答
```

`deepseek_model.py` 补上传输中漏掉的原始字段，保留 thinking 模式。程序不会生成这个推理字段，也不会填造一个字段来假装模型曾调用工具。旧程序记录无需清空；只有部分调用被任务隔离选中，或原始推理超出输入预算时，允许的工具结果会转为资料视图。完整存储记录保持不变。

### 4. 评测具体补了什么？

原自动规则可能只看到“搜索执行了、展示了一件商品、下一轮能查订单”就判通过。现在普通推荐成功场景还要求模型响应成功、任务完整完成且没有意外失败标记；保留商品证据的降级回答不能冒充推荐完成。等待订单号、权限拒绝、空结果和故意注入故障的恢复测试仍按各自预期检查，不要求所有状态都变成 `completed`。

这些检查不等于已经实现所有任务的漏工具检测。例如第五、六节说明的“没有发票调用记录”仍是通用状态收集的边界，不应因为新增推荐完成检查就宣称这一边界也已解决。

## 寒暄与按当前账号定位订单（2026-10-30）

**遇到的问题：**用户说“你好”进入业务规划后返回格式错误；说“我有一个正在退款的订单”又被要求先提供编号。日志确认前者发生了OutputParserException，后者原本只有按订单号查详情的能力，没有按当前客户定位订单的工具。
