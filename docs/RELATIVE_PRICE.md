# “有没有比这个更便宜的”多轮价格比较

## 实际问题与原因

用户先询问“推荐一款适合周末骑行的自行车整车”，系统展示商品959 Touring-3000 Blue, 58，目录标价742.3500。随后问“有没有比这个更便宜的”，系统却要求确认“排序字段”。

原记录显示第二轮在计划校验阶段被 sort_by 拦住，没有开始新的商品检索。本地日志没有保存完整失败候选，所以不能断言当时提交的具体排序值；已确认的是排序字段修改无法用原话核对。而“比这个便宜”本身还需要先确定“这个”的商品与价格，不能直接当成按价格排序或由模型猜一个预算。

这是任务条件解析与已展示商品引用的衔接问题，涉及检索之前的处理，不是本次召回排序产生了错误商品。未改动此前暂缓的长途骑行相关性算法。

## 当前怎么处理

1. 规划继续沿用原任务和用途。普通商品推荐不接收目录专用的 sort_by、sort_order、operation 字段；目录查询仍按原规则使用它们。
2. 相对价格表达交给 `relative_price.py` 规范化。“更便宜”是小于、“更贵”是大于、“不比这个贵”是小于等于，区别于“最便宜”的全目录排序和“500以内”的绝对预算。
3. 比较对象只从该任务已展示的商品中解析。只有一件时可以理解“这个”；多件时需要用户指出商品编号或第几款。模型随意填写一个ID不能代替用户选择。
4. 价格从该任务成功的 search_products、query_products、get_product_info 工具证据读取，检查 call_id、商品ID和唯一有效目录价格。不从助手回答正文提数字，不把候选池中尚未展示的商品当作比较对象，也不用历史订单成交价。
5. 程序生成数值边界，再与用户明确的预算合并。继续保留类别、数量和规格；更便宜不能自动把自行车变成配件，也不能放弃周末骑行用途。
6. 新边界仍经过现有关键词、向量召回、候选复用与最终选择的价格检查。本次没有新增业务工具或额外的相对价格分类模型。

本项目目录字段是 numeric(19,4)，因此严格低于742.3500可表示为最高742.3499；严格高于它则是最低742.3501。这是在当前目录精度下构造筛选边界，不是把商品降价，也没有假设“一分钱”或币种。不比它贵则保留742.3500作为含等号的上限。

比如用户同时说“比这个便宜，预算500以内”，用更严格的500上限。旧预算不会因比较自动取消。连续先问更便宜、再问更贵时，替换上一项推导出的比较边界，保留用户真正设置的预算及其原始依据，不让旧的临时比较永久充当预算。

缺少价格证据、多个对象无法确定、方向矛盾，或者“便宜100元/20%”等尚未实现的差额换算，继续明确澄清而不是猜值。即便有低价商品，也不保证有满足原用途的低价商品；描述依据不足时可以给出受控的无推荐说明，不以无关商品凑数。

## 到哪里维护与排查

| 文件 | 职责 |
|---|---|
| `relative_price.py` | 比较方向、已展示对象、工具价格取证、精度边界、预算交集及来源记录 |
| `task_scheduler.py` | 在计划提交前绑定旧任务并应用经过验证的比较条件 |
| `constraint_updates.py` | 按任务类型校验字段，商品推荐不接收目录排序字段 |
| `prompts/router.md` | 提醒规划保留原用途，不猜相对金额或改成全目录排序 |
| `tests/test_relative_price.py` | 严格/含等号价格、原预算、规格、歧义、假金额、失败证据及审计长度 |
| `evals/relative_price_runner.py` | 将冻结记录复制到独立测试会话，再以真实模型测试；不写原会话 |

任务的 parameter_sources 保存 reference_product_id、reference_price、reference_call_id、relation、原文和 verified_by=displayed_tool_price。parameter_changes 记录 relative_price 动作，仍限制为最近30项。现有 task_parameters_updated 事件只记录变更元数据；详细来源可查受权限保护的任务检查点或测试报告。
