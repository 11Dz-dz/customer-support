# 评分参考集怎么读、怎么用

在仓库根目录运行 `python run_judge_reference.py --render-review` 可生成同目录的逐条复核文件。文件包含固定事实，以及每条的用户问题、待评回答、预设结论和理由。

这30条是Codex编写并核对的**评分器开发参考集**，15条应通过、15条应不通过。修订后的内容和判定标准已由用户确认；没有独立专家标注。不是新的真实客服对话，也不是独立盲测集。

## 这轮解决什么问题

旧版6条校准只能检查很明显的错误，无法看出评审是否会误拒绝简短正确答案、合理澄清，或误放行价格正确但用途不符的推荐。这一版补充多订单金额互换、字段交换、遗漏请求、退款与到账、混入不合适商品、多任务等待等情况。

`fixtures.json` 给出虚构的标准事实，金额明确相加；不是生产数据库导出，商品也不是AdventureWorks真实条目。`cases.json` 保存固定问题、候选回答、预设标签和理由。每次报告记录这两份文件的SHA256和评审配置，旧报告不被覆盖。

模型只收到问题、候选回答、固定事实与一般评分要求；**不会收到预设分数、标签理由或程序规则结果**。模型返回后再与预设标签比较，避免把答案塞进提示词。

## 为什么不直接说“准确率100%”

报告分开统计：

- 误放行：预设不通过，模型却判通过。
- 误拒绝：预设应通过，模型却判不通过。
- 未评分：超时、解析失败或服务不可用；不混成0分。
- 重复不一致：同一条固定回答两次得到不同布尔分数。

这些指标表示模型与这份待人工复核标签的一致性。样本简单、数量小，并且与评分器同由Codex编写，不能替代独立标注集。即使全部一致，也不能证明复杂真实回答都能判对。S01的诚实超时回答应记为任务未完成，但原因是服务故障，不能说成虚构事实或模型理解错误。

## 金额核对具体变了什么

之前有些评分只检查“答案里出现过200”。现在新增 `evals/order_answer_facts.py`，按 **订单号＋字段＋数值** 比较独立SQL参考：

1. 明确订单12345的总额是200，另一笔12346是345.67；两个数都出现但互换，仍失败。
2. 商品编号200不能代替订单总额200。
3. 小计180、总额200不能互换。
4. 本轮没有调用工具，也可使用任务选定的订单号及历史证据定位订单，再查独立SQL核对；不信任历史结果里未经验证的金额。
5. 用户要求总额却没有提供可解析的总额，记“缺失或解析覆盖不足”，不能因为没有识别到字段而自动通过。
6. 商品报价的小计与历史订单小计分开，不用订单金额去判商品报价。

它仍不是通用中文理解器。支持已列明的金额标签、订单标题和简单段落；“这笔共计两百”等未支持表达会在要求数值的用例里进入核对失败/待复核，不能说成已证明数字错误。多笔订单没有明确金额归属时也需复核。中文数词、复杂表格、否定/引用嵌套及任意代词不保证自动识别。日期和退款状态没有在本轮改为通用事实解析器，继续使用既有规则与模型评审。

真实金额不一致属于事实错误；缺失/未解析属于覆盖问题，报告中分别记录。已有商品报价和检索评分仍保留原实现，本轮不声称所有数字匹配规则已全部替换。

## 运行

```bash
cd /root/rivermind-data/Agent/example/langgraph_olist_example

# 不需要模型、数据库或新依赖：校验30条参考集及11条金额对照，重生成可读版
/opt/conda/envs/agent/bin/python run_judge_reference.py --render-review

# 30条各评两次，只调用评审，不执行客服Agent和业务工具；会消耗DeepSeek额度
/opt/conda/envs/agent/bin/python run_judge_reference.py --live --repeat 2
```

默认报告放 `evals/reports_judge_reference/<批次>/`。报告是私有运行记录，已加入gitignore。调用前先完成参考集/规则校验；401/402/403停止本批，不自动重试到通过。

原有6条是整批客服评测前的快速冒烟，本30条独立入口用于开发和核对评审，不会默认在每道客服题前再调用60次。本轮没有更改客服Agent提示词、路由、检索或退款逻辑。
