# 追加消息后的最终答案验收

## 为什么增加

此前连续输入的真实检查验证了消息接收、预算/类别/数量参数、执行状态与回答条数，但允许通用兜底答复通过。假模型自动测试虽然检查“400的新答案替换700的旧答案”，也不能证明真实DS始终正确。因此，2026-10-31的“4个场景通过”只能说明原断言覆盖的流程通过，不能作为最终业务答案正确率。

新入口把transport_pass（流程）、business_pass（任务与最终答案）和acceptance_pass（两者均通过）分开，不能仅以输入phase=answered、Web运行completed或failure_code为空认定业务成功。

## 独立依据与评分范围

`evals/inflight_answers.py`直接读取product_catalog，按AdventureWorks整车子类别1/2/3及正标价/预算查询全量候选。不复用search_products、向量检索、排序、业务渲染器或模型输出制造标准答案，不额外调用模型裁判。

有符合商品时，检查最终任务预算、整车类别、一款数量；最后实际搜索是否应用预算和类别；答复的商品ID、名称、目录标价、数量和引用描述是否与独立SQL一致。无符合商品时，必须准确说明该预算下没有匹配整车，不接受“已检索到候选但无法确认适合”的兜底，也不能编造缺货。旧答案已经确认交付的场景，只要求追加条件后的下一份答案符合新预算，不能用后来的预算追溯判错此前合法答案。

这是一组已编写的精确业务回归，解析范围限本项目明确的“商品ID：名称”“历史目录标价”格式。未识别表达按覆盖不足失败，不冒充通用自然语言理解，也不涵盖任意骑行用途相关性、真实价格/库存或负载测试。

## 如何执行

```bash
# 默认仅显示7个用例，不访问模型或数据库
python run_inflight_answer_evaluation.py

# 显式执行真实图、模型、工具和独立SQL，并另外复核旧报告
python run_inflight_answer_evaluation.py --live \
  --historical logs/inflight-live-20261031T103406Z/report.json

# 只补测指定未执行项；失败不反复重跑挑分
python run_inflight_answer_evaluation.py --live --ids after_initial_search-1000
```

每个场景创建独立PostgreSQL Web schema及未绑定客户的临时账号，会话结束后清理自身检查点及临时schema，不改订单、商品或退款。只通过定时屏障延迟原节点，以确保第二条在目标检查点到达，不替换DS、检索返回或回答。报告保存独立SQL快照、任务状态、工具请求与证据、模型调用、最终答复、代码哈希和数据指纹。

报告目录默认evals/reports_inflight_answers，包含report.json、各场景JSON、summary.md、事件和独立historical_audit.json。原报告、原判定保持不变；旧回答复核使用当前SQL快照，不能由此声称已证明历史目录从未变化。

### 修复前批次定位的两个缺陷

1. **空检索结果与证据不足混用。** `limit_product_plan`在候选为空时统一返回no_recommendation；`render_business_result`又把它统一显示为“已检索到候选，但未能根据描述确认……”。实际没有符合预算的整车，程序却显示用途不确定。这个文案由程序生成，不能直接归因于DS胡乱作答。空结果不等于服务异常，也不等于用户需求不清楚。
2. **首轮尚未规划时连续输入，数量可能丢失。** 本批before_planning-500中DS生成的任务query为“推荐预算500以内的自行车，展示5款”，limit=5。原用户说一款。现有数量校验依据模型重写的子任务query，未在这一路径独立核对全部原始本轮输入，所以改写后的五款又被当成有效数量。其余场景保留了一款，不能据此推断每次都错或每次都正确。

500的失败不是要求在无商品时强行推荐；合格答案应如实说明在当前样例目录中，没有标价不超过500的整车。是否附带最低目录价属于可选解释，只有再次核对SQL或工具证据才可填写。

上述为修复前批次的结论；后续修复与复测单独记录，不覆盖这批失败报告。此前长途骑行相关性不在本轮修复范围，也不能把自动测试通过写成端到端业务验收通过。


## 两项缺陷的修复（2026-11-01）

**空结果分类：**回答计划增加recommendation_status，区分no_candidates（没有候选）、insufficient_evidence（有候选但用途依据不足）、invalid_selection（清单无效）和retrieval_failed（查询失败）。这些状态由程序根据证据验证，不直接相信模型自报。已有数据库/工具错误优先保留其明确错误说明。

只有检索成功但无合格候选时，程序才调用catalog_scope_summary，用无关键词、无向量排序、无LIMIT的SQL核对全目录价格/类别范围。范围确实为零，才回答“当前样例目录中，没有符合当前价格和类别条件（目录标价不超过500）的自行车整车”。范围有商品时仅说明本次完整需求未召回；核对失败时明确范围尚未核实。不会将检索失败或未召回推断成缺货，也不会为了输出推荐而从旧候选补商品。范围核对结果写入task_result摘要，并记录catalog_scope_checked/catalog_scope_unconfirmed事件。

**原始数量校验：**从当前处理段真实HumanMessage的ID选取原始输入，按时间倒序提取用户最后明确指定的展示数量。规划器返回后先修正参数，prepare_plan创建任务时再次应用，避免子任务重写成五款后覆盖原始一款。预算和“每款买两件”不会被当成展示数量；预算单独变化时保留原任务数量，用户明确改为两款则更新。多个商品任务不共享一个推断数量；表达有歧义时不强行套用其他任务或历史轮次的数量。这是限定范围的参数校验，不保证理解所有自然语言改写。

**代码职责：**answer_contract.py负责结果分类文案；task_result.py保存核对摘要；adventureworks_service.py新增精确范围只读查询；task_state.py提取本轮原始输入及明确数量；task_scheduler.py在任务创建时应用数量；langgraph_supervisor_1.py串接分类、范围核对和规划校验。tests/test_recommendation_outcomes.py覆盖失败分类、无匹配与未核实范围、原始数量和任务隔离；原连续输入假模型测试故意返回五款，验证真实用户一款仍得到保留。

检索排序、向量索引、用途相关性精选规则没有修改，不安装新依赖、不重建向量。复测继续使用原7个场景与同一评分器，不调整检查规则让新答案通过；结果另存新批次。

新增反例验证同段商品可见并可选、旧段/其他任务不可复用、降到500后原700商品被过滤、空选择不自动填充。第一次6/7不会改判；修复后使用同一7场景、同一评分器另存批次。
